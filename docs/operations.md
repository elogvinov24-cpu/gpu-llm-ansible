# Эксплуатация и диагностика

[Быстрый запуск](../README.md) · [Приёмка](acceptance.md) · [Предложения по архитектуре](architecture.md)

Ansible и `llmctl` запускайте из корня репозитория на контроллере; команды `sudo`, `systemctl`, `journalctl` и серверного Docker — на GPU-сервере. Используйте свой inventory и те же дополнительные переменные при каждом развёртывании и проверке. Если `sudo` требует пароль, добавляйте `--ask-become-pass` к Ansible-командам.

## Совместимость и ресурсы

Playbook допускает **Ubuntu Server 22.04 и 24.04 LTS, amd64**; полный прогон выполнен на Ubuntu 24.04. Нужны systemd и выделенная NVIDIA GPU либо VM с полноценным PCI passthrough. Другие версии Ubuntu, ARM/Jetson, WSL, MIG и NVSwitch не входят в поддерживаемую конфигурацию.

Для модели по умолчанию разумная стартовая конфигурация — **8 ГБ VRAM, 16 ГБ RAM и 30 ГБ свободного диска**. Это ориентир, а не гарантия: расход памяти зависит от контекста, параллелизма и других процессов. Веса выбранной квантизации занимают около 4,7 ГБ; контекст по умолчанию ограничен 2048 токенами. См. [карточку и теги Qwen2.5](https://ollama.com/library/qwen2.5/tags). Если каталоги Docker и моделей находятся на разных файловых системах, место нужно на обеих: автоматическая проверка свободного места проверяет только файловую систему `llm_data_dir`.

Проверяйте поддержку конкретной карты в [документации Ollama](https://docs.ollama.com/gpu). Проект требует драйвер версии не ниже 570; новым GPU может понадобиться более новая ветка и open kernel modules. Отдельный CUDA Toolkit на хосте не устанавливается: для контейнерного inference нужны драйвер и Container Toolkit; библиотеки модели поставляются в образе.

Требования к доступу:

- На сервере есть Python 3 и доступ по SSH от `root` или пользователя с `sudo`; SSH-ключ уже установлен.
- Контроллер: Linux/macOS, SSH-клиент, Python **3.11–3.13** с `venv` и `pip`. Команда `python3` должна запускать одну из этих версий — это диапазон для закреплённого `ansible-core 2.19` ([матрица совместимости](https://docs.ansible.com/projects/ansible/latest/reference_appendices/release_and_maintenance.html#ansible-core-support-matrix)).
- Для `./llmctl check` дополнительно нужен Docker CLI с плагином Compose; работающий Docker daemon и локальная GPU не требуются. `llmctl` не устанавливает Docker CLI на контроллер.
- Во время установки сервер имеет HTTPS-доступ к Ubuntu mirrors, Docker, NVIDIA, Docker Hub и реестру/CDN моделей Ollama. Контроллеру нужны PyPI и Ansible Galaxy.
- Предпочтителен чистый выделенный сервер. Обнаруженные конфликтующие пакеты `docker.io`, `containerd`, `runc` и другие не удаляются автоматически: сначала перенесите обслуживаемые ими нагрузки. Драйверы, поставленные вручную через `.run`, сначала приведите к пакетной установке Ubuntu.

## Подключение других сервисов

| Где работает клиент | Как обращаться к API |
|---|---|
| На GPU-сервере, вне контейнера | `http://127.0.0.1:11434` |
| В контейнере на том же сервере | После подключения к общей с Ollama Docker-сети — `http://ollama:11434` |
| На другой машине для тестирования | Через [SSH-туннель из README](../README.md#api-через-ssh-туннель), на локальный адрес туннеля |
| На других серверах постоянно | Через отдельно настроенную приватную сеть/VPN с ограничением доступа либо HTTPS gateway с авторизацией |

`localhost` внутри обычного контейнера указывает на этот контейнер. Имя `ollama` доступно только в общей Docker-сети; отдельные Compose-проекты нужно явно подключить к ней. Привязка опубликованного порта к loopback не мешает обмену внутри общей сети, поэтому подключайте к ней только доверенные сервисы. См. [сети Docker Compose](https://docs.docker.com/compose/how-tos/networking/).

Для постоянной интеграции через интернет предлагается схема **сервисы → HTTPS gateway с индивидуальными ключами и лимитами → Ollama**. Gateway на хосте может обращаться к `127.0.0.1:11434`, а gateway в контейнере — к `ollama:11434` через общую сеть. Для доверенных сервисов возможен прямой доступ через VPN без gateway, если отдельно настроить публикацию порта на VPN-адресе и firewall. Сам по себе VPN не делает loopback-порт доступным удалённо. Gateway, VPN и подключение приложений к общей сети данным playbook не настраиваются.

## Полный обзор настроек

Основные переопределения находятся в [group_vars](../inventory/group_vars/gpu_servers.yml); полный список — в [defaults](../roles/llm/defaults/main.yml). Для отдельных серверов можно создать `inventory/host_vars/gpu01.yml`.

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `llm_image` | Ollama 0.40.7 + SHA-256 | Полная неизменяемая ссылка находится в defaults и group_vars |
| `llm_model` | `qwen2.5:7b-instruct-q4_K_M` | Имя модели с явным тегом |
| `llm_model_expected_digest` | пусто | Необязательный полный 64-символьный digest из `/api/tags` |
| `llm_model_update` | `false` | Выполнить `pull` даже для уже скачанного тега |
| `llm_nvidia_driver_package` | пусто | Сохранить исправный драйвер ≥570; иначе автоматический выбор Ubuntu |
| `llm_allow_reboot` | `true` | Разрешить необходимую перезагрузку |
| `llm_secure_boot_prepared` | `false` | Подписанные модули/MOK уже подготовлены оператором |
| `llm_gpu_device_ids` | `[]` | Все GPU; можно указать список UUID или строковых индексов |
| `llm_context_length` | `2048` | Контекст по умолчанию и для smoke test |
| `llm_num_parallel` | `1` | Число параллельных запросов к модели |
| `llm_max_queue` | `32` | Размер очереди запросов |
| `llm_keep_alive` | `5m` | Удержание модели в памяти после запросов |
| `llm_port` | `11434` | Порт API на loopback хоста |
| `llm_data_dir` | `/var/lib/ollama` | Постоянное хранилище моделей и настроек Ollama |
| `llm_install_dir` | `/opt/gpu-llm` | Каталог Compose на сервере |
| `llm_container_toolkit_version` | пусто | Необязательная точная APT-версия всех четырёх пакетов Toolkit |
| `llm_docker_packages` | список Docker CE | Можно указать точные APT-версии в формате `package=version` |
| `llm_min_memory_mb` | `12000` | Минимум RAM для preflight; для меньшей модели изменяется явно |
| `llm_min_free_disk_gib` | `20` | Минимум свободного места на файловой системе моделей |
| `llm_warm_on_boot` | `true` | Прогрев и проверка модели после загрузки ОС |
| `llm_boot_ready_timeout` | `240` | Ожидание API перед прогревом, секунды |
| `llm_health_interval_seconds` | `60` | Интервал после завершения предыдущей health-проверки |

Проверочный запрос удерживает модель в памяти две минуты, чтобы успеть прочитать `/api/ps`. При нехватке памяти попробуйте меньшую модель, например `qwen2.5:1.5b`, или уменьшите контекст. Значения контекста и очереди — параметры сервера, а не полноценные квоты для недоверенных клиентов: API-запрос может менять параметры генерации.

Пример выбора одного GPU и конкретного драйвера:

```yaml
llm_gpu_device_ids:
  - GPU-REPLACE-WITH-UUID-FROM-NVIDIA-SMI
# Это пример, а не универсальная ветка для любой NVIDIA-карты.
llm_nvidia_driver_package: nvidia-driver-580-server-open
```

Выбирайте пакет по выводу `ubuntu-drivers list --gpgpu`. Playbook не меняет работающий достаточно новый драйвер при пустом `llm_nvidia_driver_package`. Автоматический выбор Ubuntu может вернуть ветку ниже заданного `llm_nvidia_min_driver`; в этом случае итоговая проверка остановит установку и потребуется явный совместимый пакет.

### Secure Boot и ручная перезагрузка

Если Secure Boot включён и требуется установка драйвера, playbook остановится до неё. Подготовьте подписанный модуль ядра/MOK по [инструкции Ubuntu](https://ubuntu.com/server/docs/nvidia-drivers-installation/) и только после этого установите `llm_secure_boot_prepared: true`. Регистрация ключа может требовать консоли/IPMI; флаг не заменяет эту процедуру. Уже работающий подходящий драйвер при включённом Secure Boot допускается.

При `llm_allow_reboot: false` драйвер может быть установлен, после чего выполнение остановится с сообщением о необходимости reboot. Можно повторить запуск в окно обслуживания с `true`. После ручной перезагрузки повторите playbook: он сравнит текущий boot ID с сохранённым маркером и автоматически распознает уже выполненную перезагрузку.

## Автозапуск и мониторинг

На сервере создаются:

- `gpu-llm-warmup.service`: запускается после Docker при загрузке ОС, ждёт API и проверяет настоящий inference на GPU. Выполняется от `nobody` с ограничениями systemd. Успешный прогрев отражается состоянием `active (exited)`; при ошибке есть ограниченные повторные попытки.
- `gpu-llm-health.timer`: примерно раз в минуту проверяет GPU хоста, Docker health, GPU внутри контейнера, наличие модели и API. Если модель загружена, проверяет её digest и VRAM. Выгруженная после простоя модель считается нормой; регулярные проверки не создают inference-нагрузку.
- `/var/lib/gpu-llm/health.json`: последнее состояние с ошибками отдельных проверок.
- `/var/lib/gpu-llm/health.prom`: статус и время последней проверки, VRAM модели, занятая/полная память GPU, загрузка и температура. Неподдерживаемые GPU-метрики пропускаются.
- `/var/lib/gpu-llm/deployment.json`: проверенные версии пакетов, драйвера, образа и digest модели. Файл меняется при изменении состава развёртывания.

```bash
# На сервере:
sudo systemctl status gpu-llm-warmup.service gpu-llm-health.timer
sudo journalctl -u gpu-llm-health.service -n 20 --no-pager
sudo cat /var/lib/gpu-llm/health.json
sudo cat /var/lib/gpu-llm/deployment.json
```

Health-процесс не перезапускает контейнеры: он сохраняет отрицательный статус, а намеренная остановка оператором сохраняется. Падение основного процесса обрабатывает Docker restart policy. При необходимости обслуживание health timer останавливается через `systemctl stop gpu-llm-health.timer`, затем возвращается через `systemctl start gpu-llm-health.timer`.

Для централизованного мониторинга подключите `health.prom` через node_exporter textfile collector. Метрики можно собирать в VictoriaMetrics через [vmagent](https://docs.victoriametrics.com/victoriametrics/data-ingestion/vmagent/); формат также совместим с Prometheus. Настройте **независимые** оповещения: проверка завершилась ошибкой (`gpu_llm_probe_success == 0`) **ИЛИ** результат устарел (`gpu_llm_probe_timestamp_seconds`), а также при отсутствии ожидаемых метрик или недоступности exporter. Любого из этих условий достаточно для отдельного сигнала; их не следует объединять логическим AND. Старый успешный снимок не должен скрывать остановку процесса или хоста. Сборщики, внешнее хранилище метрик и доставка уведомлений в этом проекте не устанавливаются. Для подробных NVIDIA-метрик можно добавить DCGM Exporter.

## Обновление, перезапуск и данные

На сервере требуется Docker Engine 28+: в более ранних версиях были ограничения изоляции портов, привязанных к localhost ([Docker port publishing](https://docs.docker.com/engine/network/port-publishing/)). Для этой конфигурации используйте стандартную bridge/NAT-сеть без включения direct routing. Уже установленный устаревший Docker playbook не обновляет автоматически и сообщает о необходимости обновления.

APT-пакеты устанавливаются с `state: present`; обычный повтор playbook не обновляет их до последних версий. Политику security updates ОС следует настроить отдельно. Образ скачивается при отсутствии; повторное применение того же тега не проверяет его изменения в registry.

Для контролируемого обновления измените `llm_image` на проверенный тег/digest и повторите развёртывание в окно обслуживания. Для обновления весов добавьте `llm_model_update: true` в файл настроек `settings.local.yml` и выполните:

```bash
ansible-playbook -i inventory/hosts.yml site.yml --limit gpu01 -e @settings.local.yml
```

Используйте тот же inventory и остальные настройки, что при установке. После успешного обновления уберите `llm_model_update` или установите `false`, чтобы обычные запуски не выполняли повторный `pull`.

При заданном `llm_model_expected_digest` новые веса должны соответствовать ему; проверка несовпадения завершится ошибкой. Обновление и проверка digest не являются транзакционным откатом: если тег изменился, новые веса уже могут быть загружены. Для production используйте внутренний registry/зеркало, зафиксированные артефакты и отдельную проверку перед переключением трафика.

Данные хранятся в `/var/lib/ollama`, независимо от жизненного цикла контейнера. При смене `llm_data_dir` перенесите данные заранее. Для отката образа верните прежний digest и повторите playbook; для отката модели нужен сохранённый артефакт/backup. Не удаляйте каталог данных при обычном обновлении.

Остановка и возобновление на сервере:

```bash
sudo docker compose --project-directory /opt/gpu-llm stop
sudo docker compose --project-directory /opt/gpu-llm up -d --wait
```

Политика `unless-stopped` восстанавливает контейнер после сбоя процесса и reboot, но учитывает намеренную остановку оператором. Docker healthcheck показывает состояние API; сам по себе статус `unhealthy` **не перезапускает** зависший контейнер. Периодический health probe фиксирует это как ошибку; восстановление выполняется оператором или внешней системой после анализа причины. Резервную копию каталога данных делайте при остановленной записи/контейнере.

## Диагностика

```bash
# На сервере:
nvidia-smi
sudo journalctl -u docker -n 100 --no-pager
sudo docker compose --project-directory /opt/gpu-llm logs --tail 100 ollama
curl --fail http://127.0.0.1:11434/api/tags
curl --fail http://127.0.0.1:11434/api/ps
```

| Симптом | Что проверить |
|---|---|
| `nvidia-smi` не работает на хосте | Reboot, Secure Boot/MOK, модуль для текущего ядра, поддержка GPU выбранной веткой |
| GPU доступен хосту, но недоступен контейнеру | Toolkit, `docker info`, runtime `nvidia`, рестарт Docker, выбранные UUID |
| HTTP работает, проверка сообщает CPU fallback | VRAM, логи Ollama, совместимость модели/GPU, `ollama ps` |
| Загрузка модели завершается по timeout | Свободный диск, доступ к registry/CDN, proxy, `llm_model_pull_timeout` |
| OOM или очень медленные ответы | Меньшая модель, контекст и параллелизм; отсутствие конкурирующих GPU-процессов |
| Туннель не открывает локальный порт | Порт 11435 занят либо SSH запрещает forwarding |

У старых сочетаний NVIDIA runtime/runc/systemd после `daemon-reload` возможна потеря GPU внутри контейнера. После проверки хостового `nvidia-smi` пересоздайте контейнер в окно обслуживания:

```bash
sudo docker compose --project-directory /opt/gpu-llm up -d --force-recreate --wait
```

Затем выполните `verify.yml`. Причины и варианты исправления, включая CDI, описаны в [NVIDIA troubleshooting](https://docs.nvidia.com/datacenter/cloud-native/container-toolkit/latest/troubleshooting.html). Не меняйте cgroup driver всего Docker-хоста без оценки остальных нагрузок.

### Cloud-init

У образов провайдера cloud-init может завершиться с кодом `2` из-за предупреждений. Playbook читает JSON-статус: допускает завершённую настройку с `WARNING`/`DEPRECATED`, выводит их в журнал и останавливается при незавершённой настройке, `errors`, `ERROR` или `CRITICAL`. Семантика кодов описана в [документации cloud-init](https://docs.cloud-init.io/en/latest/explanation/return_codes.html).
