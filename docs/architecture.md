# Предложения по архитектуре, мониторингу и защите API

[README](../README.md) · [Эксплуатация](operations.md) · [Результаты испытаний](../VALIDATION.md)

| Направление | Реализовано | Предлагаемое развитие |
|---|---|---|
| Архитектура | Ollama в Docker на каждом GPU-сервере; последовательное развёртывание через Ansible | Несколько GPU-узлов, балансировка по готовности модели и вывод узла из трафика перед обновлением |
| Мониторинг GPU | Периодические проверки GPU, контейнера и API; локальные JSON-отчёты и метрики в формате Prometheus | DCGM Exporter и node_exporter → vmagent → VictoriaMetrics; Grafana и уведомления о сбоях |
| Логи | Локальные Docker-логи с ротацией и systemd journal | Сбор логов в VictoriaLogs с ограниченным сроком хранения |
| Защита API | Порт на localhost, удалённый доступ через SSH-туннель | Приватная сеть/VPN или HTTPS gateway; firewall по адресам клиентов, API-ключи и лимиты запросов |
| Секреты и доставка | Рабочие inventory исключены из Git; GitHub Actions проверяет код и конфигурацию | Infisical для ключей сервисов; отдельный управляемый этап развёртывания после проверок |

Предложения из правой колонки **не разворачиваются данным playbook**. `serial: 1` ограничивает параллельность установки и сам по себе не обеспечивает отказоустойчивость.

Для одного GPU-сервера достаточно текущих Ansible и Compose.

## Несколько GPU-серверов

Предлагаемая схема: **бэкенд → приватный или HTTPS gateway с балансировкой → реплики Ollama/vLLM на GPU-узлах**. Перед переходом к нескольким узлам нужно проверить фактическое выделение GPU, хранение и прогрев весов, обновление модели и переключение запросов при отказе узла.

Для отказоустойчивости нужны независимые GPU-узлы с резервом ресурсов и доступными весами модели, а также устойчивый входной шлюз. Балансировщик должен отправлять запросы только на узлы с готовой моделью. Отказ единственного GPU-сервера остановит генерацию, поэтому резерв мощности нужно предусмотреть отдельно.

## Что означает защита API

Защита API определяет, кто может подключиться к модели, какие действия разрешены и сколько ресурсов можно использовать. Клиентом может быть человек с ноутбука, внутренний сервис или внешний бэкенд. Без ограничений посторонний клиент может занять очередь генерации, расходовать GPU и обращаться к административным операциям. Запросы и ответы также могут содержать конфиденциальные данные.

В текущем решении API доступен только на localhost и через SSH-туннель. Это подходит для демонстрации и ограниченного числа доверенных операторов. Ниже описаны дополнительные варианты доступа; они требуют отдельной настройки.

### Доступ для людей и сервисов

| Сценарий | Предлагаемый доступ |
|---|---|
| Один оператор проверяет модель | Текущий SSH-туннель с личным SSH-ключом |
| Сотрудники подключаются с ноутбуков | VPN с отдельными учётными данными; доступ к API через приватный шлюз, разрешённый firewall |
| Несколько доверенных сервисов внутри инфраструктуры | Приватная сеть/VPN, разрешённые адреса клиентов и индивидуальные ключи на шлюзе |
| Клиент подключается через интернет с известного IP | HTTPS-шлюз с авторизацией и firewall по фактическому исходящему IP клиента |
| Публичное приложение обслуживает конечных пользователей | Приложение проверяет пользователей и квоты; серверный ключ к LLM хранится на бэкенде, а не в браузере |

VPN даёт защищённый сетевой путь и позволяет отключить доступ конкретного участника. Firewall ограничивает адреса и порты; общий адрес офиса или NAT не идентифицирует отдельного пользователя. Авторизация на шлюзе позволяет различать клиентов и задавать им разные права и лимиты. Эти меры дополняют друг друга.

Сам по себе VPN не делает `127.0.0.1:11434` доступным удалённо. Нужен шлюз, слушающий приватный адрес и передающий запросы в Ollama, либо отдельная публикация порта на VPN-адресе. Прямой доступ в VPN подходит только доверенным клиентам: локальный API Ollama сам по себе не разделяет их права на генерацию и управление моделями.

### Дополнительные меры и их назначение

| Мера | Зачем нужна |
|---|---|
| HTTPS; при необходимости mTLS между сервисами | Шифрование запросов и ответов; mTLS дополнительно проверяет сертификат клиента |
| Индивидуальные API-ключи или пользовательская авторизация на шлюзе | Отзыв доступа одного клиента без замены общего ключа для всех |
| Разрешённый список маршрутов и методов | Оставить генерацию и необходимые операции чтения; закрыть клиентам pull/delete/create и другие административные операции |
| Лимиты частоты, параллелизма, размера запроса и генерации | Ограничить перегрузку GPU, слишком длинную очередь и расход ресурсов одним клиентом |
| Проверка формата запросов и таймауты | Отклонять некорректный ввод и ограничивать длительность обработки; шлюз должен поддерживать streaming |
| Секреты вне репозитория и регулярная ротация | Снизить последствия утечки ключа; ограничить права автоматизации и исключить секреты из вывода задач |
| Журнал доступа и оповещения | Видеть отказы авторизации, превышения лимитов и ошибки; не записывать ключи, тела запросов и ответы модели по умолчанию |

Лимиты нужно принудительно проверять на шлюзе или в приложении. Настройки контекста и параллелизма Ollama в playbook сами по себе не являются пользовательскими квотами: параметры запроса также влияют на генерацию.

Для доступа через интернет следует использовать HTTPS-шлюз: firewall сам по себе не добавляет шифрование и авторизацию. SSH и мониторинг ограничиваются адресами управления. При публикации контейнерных портов нельзя полагаться только на UFW: трафик Docker может обходить его правила. Используйте внешний firewall и/или правила для выбранного Docker firewall backend; для iptables предусмотрена цепочка [DOCKER-USER](https://docs.docker.com/engine/network/firewall-iptables/).

После настройки проверьте успешный запрос разрешённого клиента и отказ запрещённому адресу, неверному или отозванному ключу, административной операции и запросу сверх лимита. Сетевые проверки выполняются с отдельных машин, включая IPv6, если он включён. Разрешённый тестовый запрос должен по-прежнему давать ответ модели.

## Мониторинг, логи и секреты

Для ключей сервисов можно использовать [Infisical с Ansible](https://infisical.com/docs/integrations/platforms/ansible). Логи контейнеров и служб можно отправлять через сборщик в [VictoriaLogs](https://docs.victoriametrics.com/victorialogs/data-ingestion/) с ограниченным сроком хранения.

Мониторинг стоит дополнить VRAM, температурой, потреблением мощности, XID/ECC, заполнением диска и задержками API. Доступность метрик зависит от GPU; см. [DCGM Exporter](https://docs.nvidia.com/datacenter/dcgm/latest/gpu-telemetry/dcgm-exporter.html). Доступ к метрикам следует ограничить сетью управления.

## Подготовка к эксплуатации

Базовый сценарий проверен на Ubuntu 24.04/L4 — см. [VALIDATION.md](../VALIDATION.md). Перед использованием под рабочей нагрузкой рекомендуются дополнительные проверки:

- **Нагрузка:** измерить время первого токена, p95 задержки, tokens/s и VRAM при холодном старте, параллельных запросах и длительной работе. Подобрать лимиты под требования продукта; проверить отсутствие OOM и CPU fallback. При высокой конкурентности сравнить Ollama с [vLLM](https://docs.vllm.ai/en/latest/serving/openai_compatible_server/).
- **Несколько клиентов:** выбрать VPN/firewall и шлюз с индивидуальной авторизацией, правами и квотами. Проверить разрешённый доступ, отзыв ключей, запрет административных операций, streaming и поведение при превышении лимитов. Подробнее — [защита API](#что-означает-защита-api).
- **Другие конфигурации и обновления:** повторить установку, проверку идемпотентности, reboot-test и GPU inference на каждой используемой комбинации Ubuntu/GPU/драйвера. Отдельно испытать обновление и откат; Ubuntu 22.04, Secure Boot и несколько GPU пока не проверены.

Это рекомендации по дальнейшему развитию; расширенные испытания и дополнительные средства доступа в рамках текущего решения не выполнялись и не развёртывались.
